Skill Publisher
The workflow for turning a reusable pattern into a published portal skill. Use whenever a skill or walkthrough is created, installed, or modified and needs to appear on the knowledge portal. Triggers on 'add this as a skill', 'publish this skill', 'add to the portal', 'create a walkthrough'.

Use this skill to publish content to the GitHub Pages knowledge portal at gilesparnell/Claude. Covers skills, walkthroughs, and templates.

Portal URL: https://gilesparnell.github.io/Claude/ Repo: public portal checkout (local) / gilesparnell/Claude (remote, PUBLIC)

⚠️ Repo split: gilesparnell/Claude is now a PUBLIC repo containing only skills, walkthroughs, templates, and portal pages. Decision records are NOT published to the portal anymore — they live in a private operations repo. Never copy decisions, memory, identity, pricing, or client content into the public repo. The public repo has a pre-commit scan hook that blocks private terms — if it fires, stop and reassess; never bypass it.

Portal Structure

The portal has multiple content types, each with its own page and file location:

Content Type Portal Page Source Files How Cards Work
Skills docs/skills.html skills/<slug>/SKILL.md Index + docs/skills/<slug>.html detail page auto-generated by GitHub Action
Walkthroughs docs/walkthroughs.html docs/diagrams/<slug>.html Manual — add card HTML + detail page
Decisions (not on the public portal) Private operations repo decision files Private only — no page
Templates docs/templates.html project-templates/<slug>/CLAUDE.md Card in HTML is manual; docs/templates/<slug>.html detail page auto-generated by Action

Shared design system: docs/portal.css — all pages import this. Never create custom CSS.

The build-portal GitHub Action owns the generated files. On every push touching skills/**, project-templates/**, scripts/**, or the walkthrough/template HTML, it runs node scripts/build-docs-index.js, which regenerates docs/docs-index.json and every docs/skills/<slug>.html + docs/templates/<slug>.html page, then auto-commits ([skip ci]). Never hand-edit docs/docs-index.json or anything under docs/skills/ or docs/templates/ — it will be overwritten. Edit the source SKILL.md / CLAUDE.md and push; the page rebuilds itself. Run npm test + npm run build locally first to preview.

Part 1: Publishing a Skill

MANDATORY RULE

Every skill that is created, downloaded, installed, or modified MUST be:

  1. Committed to git — pushed to the gilesparnell/Claude repo
  2. Added to the knowledge portal — portal stub in skills/<slug>/SKILL.md

This applies to ALL skill origins:

  • Skills you write from scratch
  • Skills installed from plugins or marketplaces
  • Skills downloaded or copied from external sources
  • Skills generated by any AI agent (Claude, Codex, etc.)
  • Skills modified or updated (commit the update + update portal stub version)

Two Formats — Always Create Both

1. Runtime version — ~/.claude/skills/<slug>/SKILL.md

What Claude reads when the skill is invoked. Full markdown content.

---
name: <slug>
description: Use this skill when... Triggers on '<phrase 1>', '<phrase 2>'.
---

# Skill Title

[Full instructions, principles, checklists, examples, gotchas]

2. Portal SKILL.md — skills/<slug>/SKILL.md

What the portal renders. Portal frontmatter (below) plus the full markdown body — on push the build-portal Action generates a docs/skills/<slug>.html detail page from it. Frontmatter drives the card + page header (title, icon, triggers, checks); the body becomes the page's main content. A frontmatter-only file renders an empty page, so include the body.

---
title: Display Title
scope: global | project
category: code | workflow | frontend | saas | tooling | engagement
icon: [emoji HTML entity]
description: One sentence. What it does and when to use it.
triggers:
  - phrase that invokes this
  - another trigger phrase
checks-label: Principles | Steps | Checks | Rules
checks:
  - Key point 1
  - Key point 2
  - Key point 3
  - Key point 4
version: 1.0
---

Scope Decision

Scope Location When
Global ~/.claude/skills/<slug>/ Useful on any project
Repo-specific <project>/.claude/skills/<slug>/ References a specific tech stack, client, or workflow

The portal stub always goes in skills/<slug>/ regardless of scope.

Skill Step-by-Step

  1. Draft the runtime SKILL.md — write it as instructions to yourself: principles, checklist, examples, gotchas.
  2. Choose a slug — lowercase, hyphenated, descriptive. payment-webhooks not payments.
  3. Place the runtime file in the correct scope location (global or repo-specific).
  4. Create the portal SKILL.md at skills/<slug>/SKILL.md — portal frontmatter (title, scope, category, icon, triggers, checks ≤ 4) followed by the full body (usually the same content as the runtime file).
  5. Preview locally: run npm test && npm run build from the public portal checkout — confirm docs/skills/<slug>.html generated and looks right. Do NOT commit docs-index.json/docs/skills/ by hand; the build regenerates them.
  6. Commit and push the skills/<slug>/SKILL.md (see "Git Push Protocol"). The build-portal Action rebuilds the index + detail page and auto-commits them.
  7. Verify the skill appears in Claude Code's skill list (system reminders) and its page is live at gilesparnell.github.io/Claude/skills/<slug>.html.

Step 4: Commit and push

See "Git Push Protocol" below.

Git Push Protocol

This is the same for all portal content — skills, walkthroughs, decisions, templates.

cd <public-portal-checkout>
git pull --rebase origin main          # ALWAYS pull first
git add [files]                        # Stage specific files
git commit -m "feat: add <slug> [skill|walkthrough|decision]"
git push origin main

If the push is rejected (remote has newer commits):

git stash
git pull --rebase origin main
git stash pop
git push origin main

Do NOT force push. If conflicts arise, resolve them manually.

Completion Checklists

Skill Checklist

  • Runtime SKILL.md exists in ~/.claude/skills/<slug>/ (or repo-scoped equivalent)
  • Portal stub exists in skills/<slug>/SKILL.md
  • Portal stub has correct frontmatter (title, scope, category, icon, description, triggers, checks, version)
  • Changes committed to gilesparnell/Claude repo
  • Changes pushed to origin/main
  • Skill appears in Claude Code's skill list (verify by checking system reminders)

Walkthrough Checklist

  • Detail page exists at docs/diagrams/<slug>.html
  • Detail page uses portal.css (no custom CSS), has correct header/nav/footer
  • Card added to docs/walkthroughs.html BEFORE the empty state placeholder
  • Card has correct data-category, thumbnail, title, description, tags, link
  • Hero stats count updated in docs/walkthroughs.html
  • Changes committed to gilesparnell/Claude repo
  • Changes pushed to origin/main

If any of these are incomplete, the task is not finished. Do not move on to other work.

Gotchas

  • The description field in skill runtime frontmatter is what Claude Code uses for trigger matching — make it specific and include example trigger phrases in quotes
  • Don't make skills too broad — coding is useless; nextjs-api-routes is useful
  • If a skill is repo-specific, do NOT add a runtime version to ~/.claude/skills/ — it'll trigger incorrectly on other projects
  • Portal stubs with more than 4 checks look cluttered — curate ruthlessly
  • Keep the portal stub and runtime slug identical so they're easy to cross-reference
  • Walkthrough cards MUST go before the <!-- EMPTY STATE --> comment in walkthroughs.html
  • Walkthrough thumbnails should be visual (mini-diagrams), not plain text
  • Always use ../portal.css (relative path) in walkthrough detail pages
  • SVG diagrams can use hardcoded fills but inline styles should use CSS variables where possible
