Frameworks
Spec-driven development systems for Claude Code — run and read first-hand, not summarised from someone else's take.
GSD CoreACTIVE

A set of slash commands for Claude Code that turn "build me X" into a fixed sequence: agree the decisions, write a plan, have the plan checked, build it in small committed steps, then prove it does what you asked. Each step writes a plain Markdown file, and the next step reads it. Claude never has to remember anything between sessions, because it's all on disc.

Repo: open-gsd/gsd-core Runs on: Claude Code, Codex, Gemini CLI, Cursor + others Running here: v1.13.0
npx -y @opengsd/gsd-core@latest --claude --local
⚠

Install from the right repo. Articles ranking GSD by star count point at gsd-build/get-shit-done, which was archived on 31 May 2026. Development moved to open-gsd/gsd-core. The command above installs the live one.

01 · Why bother: the problem it fixes ↑ contents
Without it — a long chat with Claude
  • Decisions get lost. You agreed something 40 messages ago; the context window dropped it.
  • "Done" means "finished typing". The code runs, and nobody checked it answers the question you asked.
  • One model checks its own work. It has the same blind spots writing the test as writing the code.
  • Starting a new session means re-explaining everything from scratch.
With it — a fixed loop, written down
  • Decisions are numbered (D-01, D-02…) and every plan has to reference them, or the plan is rejected.
  • Each phase ends with a check against its goal, with you in the loop, and fix plans written for anything that fails.
  • A different AI can review the plans before a line of code exists (section 04).
  • A fresh session reads STATE.md and carries on where the last one stopped.

03 · What it looks like in the terminal ↑ contents

One phase, condensed from a real run. You type the green lines. Everything else is Claude, its subagents, or files landing in .planning/.

claude — ibkr-dashboard

  Grey area: when should the screen say the data is out of date?
  ...you answer in plain English; nothing is built yet...

> /gsd-plan-phase 2
  researcher  → 02-RESEARCH.md
  planner     → 02-01-PLAN.md .. 02-12-PLAN.md
  checker     → every decision referenced? every requirement owned?  pass

> /gsd-review --phase 2 --cursor
  cursor (a non-Claude model) reviewing 12 plans...
  wrote 02-REVIEWS.md  HIGH concerns found

> /gsd-plan-phase 2 --reviews
  planner revises; each finding marked incorporated / deferred / rejected, with a reason

> /gsd-execute-phase 2
  wave 1 ... wave 7   fresh agent per plan, one commit per task

> /gsd-code-review 2   → 02-REVIEW.md   8 findings
> /gsd-code-review 2 --fix  → 8 fixed, 8 commits

> /gsd-verify-work 2
  Test 1: In IB Gateway's settings, Read-Only API is ticked. Does it match?
> pass
04 · Getting a second AI to check the work ↑ contents

This is the part with no equivalent in a normal Claude chat. When the same model writes the plan and checks the plan, it shares its own blind spots. GSD sends the finished plans to a different AI, from a different company, running in its own command-line tool. Its findings come back as a file, and Claude has to answer every one in writing before any code gets built.

A finding from the reviewDecisionWhy it mattered
The sign of avg_cost is never pinned down. Is a sold option's cost stored as a credit or a debit? incorporated Left open, the break-even price would have been calculated backwards, and the tests would still have passed because they used the same wrong assumption. No amount of Claude re-reading its own plan was going to find this one.
Rename the test-first commit convention. rejected The rename would have erased the "test written and failing first" evidence the project's rules require. The useful half of the point was kept. A reviewer finding is input, not an order.
Turning it on

Install at least one other AI's command-line tool and log in (Codex CLI, Gemini CLI, or Cursor's cursor-agent). GSD detects whichever are installed. Then pin the models and pick a default in .planning/config.json:

.planning/config.json
"review": {
  "models": {
    "codex":  "gpt-6.1-sol",
    "gemini": "gemini-3.5-flash",
    "cursor": "gemini-4-argon-high"
  },
  "default_reviewers": ["cursor"]
}

After that it's two commands per phase: /gsd-review --phase N (or --codex, --gemini, --all), then /gsd-plan-phase N --reviews. Or hand the whole loop over with /gsd-plan-review-convergence N. That command refuses to run until workflow.plan_review_convergence is set to true (section 09).

A second AI on the code, too

Plan reviews catch design mistakes. They can't see bugs that only appear once code exists, and GSD's built-in code review is Claude checking Claude. /gsd-ship has a hook for this: set workflow.code_review_command and the whole diff is piped to that command, which must answer with JSON containing "verdict": "APPROVED" or "REVISE". GSD doesn't include a command that talks to another AI, so I wrote a small one: gsd_cross_ai_review.py. It hands the diff to Cursor's CLI in read-only mode and returns the verdict. If anything goes wrong it reports a failure; it never quietly approves.

Its first live test was a deliberately planted bug: a short put's break-even changed from strike − premium to strike + premium. It took 31 seconds:

diff → gsd_cross_ai_review.py → cursor-agent
$ git diff main...HEAD | python3 gsd_cross_ai_review.py --model gemini-4-argon-high
{
  "verdict": "REVISE",
  "confidence": 100,
  "summary": "...changed from `strike - premium` to `strike + premium`,
              which is the formula for a call option rather than a put option.",
  "issues": [{ "severity": "high", "file": "calc.py",
               "suggestion": "Keep `return strike - premium`." }]
}

The command /gsd-ship really runs builds a fuller prompt (diff stats, phase state, the JSON shape it wants) and pipes that in. The one-liner above shows the idea.

Lesson
Use a different model family each round
  • Round 2 should look at the fixes with fresh eyes, not the same ones that suggested them
Lesson
Cheap tiers fail on big plan sets
  • Codex on a ChatGPT Plus plan and Gemini's free tier both failed on a large plan set; Cursor handled it
  • A reviewer that can't run is recorded as a failure, not quietly dropped
Lesson
Spend it where mistakes cost money
  • Roughly 8 minutes per reviewer per phase
  • Worth it for maths, money and login code; skip it for cosmetic work
The checker matters more than the planner. GSD's default setup put its own internal plan-checker on the cheapest model. That checker said "all findings incorporated" while missing all three rejections. Run on a stronger model, it found one fix had reached only 7 of the 11 places it needed to. Set model_overrides so the checker isn't the weakest link.
05 · The phase loop, step by step ↑ contents

Nine possible steps per phase. Two are genuinely required. The rest are checks you add when a phase is risky, vague, or expensive to get wrong.

#StepWhy you'd run itWeight
1/gsd-discuss-phase N Captures design decisions as numbered D-NN records. Everything after is checked against them, so a decision never captured is never built. recommended
2/gsd-spec-phase N Scores how vague the scope still is and pins down what the phase delivers. Worth it when "done" is still fuzzy after discussion. optional
3/gsd-plan-phase N Researches, writes the plans, and runs a checker over them. The core command. required
4/gsd-review --phase N
/gsd-plan-phase N --reviews		 A different AI audits the plans, then the findings are folded back in. See section 04. recommended
5/gsd-execute-phase N Builds the plans in dependency order, one commit per task. required
6/gsd-code-review N
/gsd-secure-phase N		 Checks over the code just written: bugs and quality, then whether the security risks the plan named were actually handled. optional
7/gsd-verify-work N You test it, one check at a time, against the phase's goal. Anything that fails gets diagnosed and a fix plan written automatically. recommended
8/gsd-extract-learnings N Pulls decisions, lessons and surprises out of the finished phase so later phases inherit them. optional
9/gsd-ship N Opens the pull request with a body built from the requirements and verification. optional

07 · Gates, and which ones actually block ↑ contents

Not every check stops the run. Knowing which ones really block saves arguing with the ones that don't.

Blocking
Decision coverage
  • Every D-NN must be referenced by a plan
  • Won't mark a phase planned if a decision was silently dropped
Blocking
API coverage
  • Every capability of an external API is marked "use" or "opt out, because…"
  • Testing won't start until the list is complete
Blocking
Phase completion
  • A phase isn't complete until every human test has passed and verification is current
Advisory
Plan-checker
  • ~12 checks over the plan set
  • Blockers force a rewrite, up to 3 rounds
Advisory
Requirements coverage
  • Every requirement assigned to a plan
  • Offers re-plan / defer / accept
Scripted, no AI
Verify-command probes
  • Do the test commands in each plan actually exist and run?
  • These return exit codes, not opinions
Scripted beats clever. When an AI-driven check disagrees with a scripted one, believe the script.
08 · A real build: an IBKR options dashboard ↑ contents

A read-only web app on a live Interactive Brokers account. It answers one question IBKR's own screens don't: if every put I've sold gets exercised, does my cash cover it? The requirements were drafted before GSD was installed. Here's the kind of vagueness the questioning step pulled out of them:

01"Max puts sellable without liquidation risk"
The broker's own margin limit (what actually triggers liquidation), or a self-imposed cash-secured limit the broker doesn't enforce at all? Mixing those two up is the most expensive ambiguity on the list.
02"Potential profit on existing calls and puts"
Today's paper profit if closed now, or how much of the premium has been earned toward the maximum? Different numbers.
03"Income from options, week by week"
Only closed trades, or does it move with open positions too?
04"Annualised % return"
Against the whole account, or only the cash tied up that week? On this account, the share of cash in use swung between roughly 3% and 96% in a single session, so the choice changes the answer enormously.

That became a seven-phase roadmap, with one phase (a strike-price advisor) inserted mid-way. Status as of 23 Oct 2026:

09 · Switches worth turning on ↑ contents

Out of the box, GSD runs the core loop and leaves several of its best checks off or waiting to be run by hand. These are the eight I switched on for the dashboard, ordered by how much they're worth on something that touches real money. "Automatic" means GSD runs it at that point in the loop once the setting is on.

#WhatHow to turn it onWhat you get
1Security review workflow.security_enforcement: true
automatic after testing		 Checks every risk named in the plans was actually dealt with in the code. Open high-severity risks block the phase from shipping. Run /gsd-secure-phase N for phases that closed before it was on.
2Second AI on the code workflow.code_review_command
automatic at /gsd-ship		 The whole diff goes to a different AI before the pull request opens (section 04). Needs a bridge script such as this one.
3Review → revise loop workflow.plan_review_convergence: true
command		 Unlocks /gsd-plan-review-convergence N, which repeats review and revision until no HIGH concerns remain, and the --converge option on /gsd-next and /gsd-autonomous.
4Lessons carried forward /gsd-extract-learnings N
command after each phase		 Writes LEARNINGS.md: decisions, surprises and patterns from the phase, read by the planner for later phases. No setting; make it a habit when a phase closes.
5Pin down "done" first /gsd-spec-phase N
command before planning		 Worth it on any phase with a fixed external contract (a file format another program reads, an API you don't control). It keeps asking until the scope is tight enough, then writes testable statements.
6Testing checks the screen itself workflow.live_dom_uat: true
automatic during build and test		 With a browser tool connected (Claude in Chrome or Chrome DevTools), GSD opens the app, checks what it can see, and only asks you about the parts that need human judgement.
7Codebase map /gsd-map-codebase once
workflow.plan_drift_precheck: true		 Writes a set of documents describing the code (structure, conventions, concerns) that planners read. The drift check warns before planning when the map has gone stale.
8UI review workflow.ui_review: true
automatic after testing		 A visual audit of the screens against the phase's design spec, scored across six areas, on any phase that built UI.
Make them the default for every new project. GSD reads ~/.gsd/defaults.json when it creates a project, so settings put there apply from day one. Mine:
~/.gsd/defaults.json
{
  "workflow": {
    "security_enforcement": true,
    "code_review_command": "python3 /Users/you/.claude/scripts/gsd_cross_ai_review.py --model gemini-4-argon-high",
    "plan_review_convergence": true,
    "live_dom_uat": true,
    "ui_review": true,
    "plan_drift_precheck": true
  },
  "review": {
    "models": { "cursor": "gemini-4-argon-high", "codex": "gpt-6.1-sol", "gemini": "gemini-3.5-flash" },
    "default_reviewers": ["cursor"]
  },
  "model_overrides": { "gsd-plan-checker": "sonnet" }
}

For a project that already exists, set the same keys with /gsd-config, or edit .planning/config.json. Use an absolute path in code_review_command: /gsd-ship does not expand ~.

10 · Starting your own project ↑ contents
Install into the repo. npx -y @opengsd/gsd-core@latest --claude --local. Commands appear in Claude Code as /gsd-….
Describe the project. /gsd-new-project for a fresh idea, or /gsd-onboard if there's already code. Answer the questions properly: this is where most of the value is.
Run the first phase: /gsd-discuss-phase 1 → /gsd-plan-phase 1 → /gsd-execute-phase 1 → /gsd-verify-work 1.
Add a second AI before the phase that matters. Install Codex, Gemini or Cursor's CLI, set review.default_reviewers, and run /gsd-review between plan and execute. For a trading tool, that's the phase where the maths or the money logic gets written.
Switch on the extra checks. Copy the defaults.json from section 09 before running /gsd-new-project, and every project starts with security review, second-AI code review and the rest already on.
Lost? /gsd-progress or /gsd-next. Both read the files on disc and tell you the next command. After a /clear or a new session, start here.
