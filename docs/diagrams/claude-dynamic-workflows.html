Claude's Dynamic Workflows
The Workflow tool runs a deterministic script that orchestrates many subagents — pipeline vs parallel, the quality patterns worth stealing, and the guardrails that keep it from running away.
What a dynamic workflow actually is
📜
A script, not another agent
Workflow runs plain JavaScript — loops, conditionals, fan-out are ordinary code, not something a model decides on the fly. The script calls agent(), parallel() and pipeline() to spawn and sequence subagents. It runs in the background: a task notification arrives when it finishes, and /workflows shows live progress.
🔒
Opt-in, never the default
It only fires on explicit signal — the word "ultracode" in a prompt, ultracode switched on for the session, a direct ask to "use a workflow" or "fan out agents," or a skill whose instructions call for it. Everything else gets a single Agent call or none at all. A workflow can spawn dozens of subagents; that scale needs the user's say-so, not an inference.
📏
Scale to what was actually asked
"Find any bugs" → a handful of finders, one verification vote each. "Thoroughly audit this" or "be comprehensive" → a larger finder pool, a 3–5 vote adversarial pass, a synthesis stage. The size guideline is configurable per session (default: keep it under ~15 agents) — a guideline, not a hard ceiling.
The core building blocks
agent()
Spawn one subagent
Returns the subagent's final text as a string — or, with opts.schema set, a validated object. Schema forces the subagent to call a structured-output tool, so the parent gets typed data back instead of prose to parse. opts.phase and opts.label control where it lands in the progress tree; opts.isolation:'worktree' gives it its own git worktree when agents will edit files in parallel and would otherwise collide.
pipeline()
The default: no barrier between stages
Every item runs through all stages independently. Item A can be in stage 3 while item B is still finishing stage 1 — wall-clock time is set by the slowest single item's full chain, not by the sum of each stage's slowest item. This is the shape almost all multi-stage work should take.
parallel()
A genuine barrier
Runs a set of thunks concurrently and awaits every one before returning. Correct only when stage N truly needs the complete set of stage N−1 results at once — deduplicating findings, an early-exit on a zero count, or a prompt that references "the other results." A thunk that throws resolves to null rather than failing the whole call.
phase() / log()
Narration, not logic
phase(title) groups every subsequent agent() call under a titled heading in the live progress view. log(message) prints a one-line narrator update above the tree. Neither affects control flow — they exist purely so a human watching /workflows can follow along.

Same three items, same per-item durations. pipeline() lets each item run its own chain start to finish; parallel() forces every item to clear stage 1 before any item starts stage 2. Here that difference is 60 units versus 100.

When a barrier is actually justified
✓
Stage N genuinely needs all of stage N−1
Deduplicating or merging findings across the full result set before expensive downstream work; an early-exit when the total count is zero ("0 bugs found → skip verification entirely"); a prompt that explicitly compares one item against "the other findings."
✗
Reasons that don't actually justify one
"I need to flatten or map the results first" — do that transform inside a pipeline stage, no barrier required. "The stages are conceptually separate" — that's what pipeline() already models. "It's cleaner code" — the latency is real: if five finders run and the slowest takes 3× the fastest, a barrier wastes two-thirds of the fast finders' idle time.
Quality patterns worth stealing
⚖️
Adversarial verify
Spawn N independent sceptics per finding, each prompted to try to refute it, defaulting to "refuted" when uncertain. Kill the finding if a majority refute. Stops plausible-but-wrong findings from surviving on the strength of one confident agent.
🎯
Perspective-diverse verify
When a finding can fail in more than one way, give each verifier a distinct lens — correctness, security, performance, does-it-actually-reproduce — instead of N identical refuters. Diversity catches failure modes redundancy can't.
🏆
Judge panel
Generate N independent attempts from different angles — MVP-first, risk-first, user-first — score them with parallel judges, then synthesise from the winner while grafting the best ideas from runners-up. Beats iterating on a single attempt when the solution space is genuinely wide.
🔄
Loop-until-dry
For unknown-size discovery — bugs, edge cases, issues — keep spawning finders until K consecutive rounds turn up nothing new that isn't already in the seen set. A fixed while count < N loop misses whatever's in the tail.
🔎
Multi-modal sweep
Parallel agents each search a different way — by container, by content, by entity, by time — blind to what the others surface. Useful whenever one search angle alone won't find everything.
👀
Completeness critic + no silent caps
A final agent asks "what's missing — a modality not run, a claim not verified, a source not read?" — its output becomes the next round. And if a workflow bounds coverage (top-N, no retry, a sample), log() what was dropped; a silent cap reads as "covered everything" when it didn't.
The canonical shape: review → verify, no wasted wall-clock
// each dimension verifies as soon as ITS review completes — 'bugs' findings
// start verifying while 'perf' is still being reviewed. No barrier, no wasted time.
const results = await pipeline(
  DIMENSIONS,
  d => agent(d.prompt, { label: `review:${d.key}`, phase: 'Review', schema: FINDINGS_SCHEMA }),
  review => parallel(review.findings.map(f => () =>
    agent(`Adversarially verify: ${f.title}`, { label: `verify:${f.file}`, phase: 'Verify', schema: VERDICT_SCHEMA })
      .then(v => ({ ...f, verdict: v }))
  ))
)

const confirmed = results.flat().filter(Boolean).filter(f => f.verdict?.isReal)
return { confirmed }
Guardrails and limits
⏰
Concurrency and lifetime caps
At most min(16, cores − 2) agents run concurrently per workflow — excess calls queue and run as slots free up, so passing 100 items still completes, just throttled. Total agent count across a workflow's life is capped at 1000, a backstop against a runaway loop. A single parallel()/pipeline() call caps at 4096 items.
💾
Resume from a run ID
A paused, killed, or edited workflow can be relaunched with its prior runId. The longest unchanged prefix of agent() calls returns cached results instantly; only the first edited call and everything after it re-runs live. Same script, same args → a full cache hit.
💰
Token budget as a hard ceiling
When the user gives a target ("+500k"), budget.total/budget.spent()/budget.remaining() are available inside the script for loop-until-budget patterns. It's enforced, not advisory — once spend hits the target, further agent() calls throw.
⚠️
Plain JS, no wall-clock inside the script
Scripts are JavaScript, not TypeScript — type annotations and generics fail to parse. Date.now(), Math.random(), and argless new Date() all throw, because they'd break resume determinism. Pass timestamps in via args and stamp results after the workflow returns.
Single agent, or a workflow?
🧩
One Agent call
The default for everything: a self-contained lookup, a scoped fix, one investigation whose answer feeds the next step directly. No opt-in needed, no progress tree to watch.
🌐
A Workflow script
Comprehensiveness across many independent pieces, confidence from adversarial cross-checking before committing to a finding, or scale one context window can't hold — and always because the user asked for that scale, in their own words or by having ultracode on.
